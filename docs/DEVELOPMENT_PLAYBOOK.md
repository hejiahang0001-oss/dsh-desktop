# DSH Desktop 开发与迭代手册

本手册是 DSH Desktop 每个版本的默认执行规范。它约束产品切片、代码边界、测试、审查、打包、覆盖安装、发布和 Wiki 回写；版本计划记录“做什么”，本手册规定“怎么做”。

## 1. 版本迭代原则

1. 每个小版本只解决一个可观察的核心问题，可以包含为闭环所需的测试、文档和安全修复。
2. 开始前先核对官方 DeepSeek Harness 的最新能力；若上游已完整提供，优先适配或删除桌面重复实现。
3. Harness 负责 Agent loop、会话、模型、权限、队列、Skills、Plugins、Hooks、MCP 和主 Web UI；DSH 负责 Windows 宿主、原生窗口、文件/终端/审阅/Office/Wiki、安装升级和恢复。
4. 不同时升级多个高风险基础依赖。Harness、Electron、Node、pnpm 分开升级，分别建立兼容证据。
5. Stable 不随日常迭代自动变化。日常开发推进本地 Latest 候选；公开 Pre-release 和 Stable 晋升分别需要显式确认。
6. 计划、已实现、已验证、已安装、已公开必须分开描述，不能用源码完成替代交付完成。

## 2. 每版固定流程

### A. 定义切片

- 写清用户问题、目标行为、明确不做的内容和涉及的产品边界。
- 标注发布通道：本地候选、公开 Pre-release 或 Stable 晋升。
- 列出会受影响的会话、Workspace、用户数据、凭据、代理、插件和安装兼容面。

### B. 核对上游与现状

- 固定 Harness tag、commit、package count、锁文件和构建来源，不使用浮动 `latest`。
- 比较上游能力与 DSH 现有实现：完全重复则使用官方；只覆盖一部分则保留最小桌面补充并写清边界。
- 读取相关模块、相邻测试、最近发布说明和已知限制；禁止为一个局部问题做无关重构。

### C. 先写验收条件

- 至少覆盖正常路径、空状态、错误路径、取消、竞态、切换会话/Workspace 和恢复路径。
- Bug 修复先添加能复现原问题的回归测试；新交互先定义可见状态、键盘、焦点和失败反馈。
- 高风险操作补充默认取消的原生确认和确认后的状态重检。

### D. 实现

- 将策略和可测试逻辑放入独立 `.cjs` 模块；`electron/main.cjs` 负责组合和生命周期，不继续堆叠可独立测试的业务逻辑。
- Renderer 只调用窄、固定、可验证的 Preload 能力；不向 Renderer 暴露任意路径、命令、包规格、令牌或通用文件接口。
- 状态改变前后都重新确认会话、Workspace、窗口所有者或资源指纹，防止用户切换造成跨上下文写入。
- 持久状态使用原子写入、已验证备份和失败恢复；敏感数据不进入日志、普通备份、截图或子进程环境。

### E. 源码验证

- 运行针对本次变更的测试，再运行完整 `pnpm test`。
- 运行 `pnpm audit --prod --audit-level moderate`；Electron/Chromium 支持状态另行核对，不能只依赖依赖审计。
- UI 变化至少检查正常、窄窗口/高缩放、键盘焦点、强制色或高对比、减少动画和错误状态。
- Harness 交互变化必须在真实官方页面验证；涉及模型、工具、排队或权限时增加真实会话证据。

### F. 代码审查

- 先看用户目标和架构边界，再逐文件检查逻辑、错误、竞态、安全、性能、数据保留和测试。
- 审查意见按 Blocking、Important、Nit、Suggestion 分级；Blocking 必须修复后才能进入打包。
- 格式、导入排序和机械问题交给工具；审查不因个人风格阻断，也不顺手扩大版本范围。

### G. 打包与安装态验证

- 更新 `package.json` 版本、对应 `docs/RELEASE_NOTES_vX.Y.Z.md`、README 下载名和 PROGRESS 证据。
- 生成 NSIS/Portable 产物，记录名称、字节数和 SHA-256；检查打包内容、依赖闭包、许可证、链接和敏感文件。
- 对解包应用执行基础与专项冒烟。
- 覆盖安装前创建不含凭据的回滚快照和语义数据摘要，然后覆盖旧版。
- 对已安装应用重复 Harness 启动、Workspace 同步、本次功能和用户数据保留验证。失败时不得宣称版本完成。

### H. 发布与知识回写

- 本地候选验证通过不等于 GitHub 发布。公开 Pre-release、资产上传和 Stable 晋升必须分别确认。
- 公开后核对 CI、Release draft/prerelease 状态、每个远端资产的大小/SHA-256 和匿名下载 HTTP 状态。
- 更新 DSH Wiki：版本总览、所属阶段页、能力演进、Harness 兼容、发布通道、来源哈希、日志和近期摘要。
- 根据本轮问题调整后续版本顺序，但不把未完成事项写成已交付。

## 3. JavaScript / Electron 代码规范

### 文件与语言

- 延续 CommonJS `.cjs`：`require` / `module.exports`；Node 内置模块使用 `node:` 前缀。
- 默认使用 `const`，只有确需重新赋值时使用 `let`；保留分号和单引号，与相邻文件一致。
- 常量使用可说明边界的名称，例如 `MAX_*`、`REQUIRED_*`；不要在流程中散落魔法数字。
- 函数保持单一职责；先校验后执行，优先早返回，避免多层嵌套。
- 捕获异常时只忽略明确、可接受的错误码；其他错误继续抛出并由上层转为用户可理解的状态。

### 模块边界

- `electron/main.cjs` 只做窗口、生命周期和模块接线；新的策略、存储、解析或控制器进入独立模块并导出可测试函数。
- Preload API 使用按能力分组的固定方法；每增加一个方法，同时增加允许/拒绝矩阵测试。
- 主进程的特权操作必须验证预期 `webContents`、精确主 Frame、允许 URL，并在需要时绑定 Frame owner。
- Harness 官方交互所有权由回归测试保护；不得重新拦截官方队列、Steer、Stop 或主输入协议。

### 输入、路径与资源

- 所有来自 Renderer、文件拖放、会话、插件、网络和远端 API 的输入都视为不可信。
- 路径必须绝对化/规范化后验证在允许根目录内；拒绝遍历、符号链接、目录联接、备用数据流、保留名和大小写碰撞。
- 文件处理设定格式、签名、数量、单文件大小、总大小、深度和时间上限。
- Renderer 只得到显示所需的受限元数据或短期不透明 ID；真实路径、会话内部 ID 和凭据留在主进程。

### 状态、并发与恢复

- 写入操作串行化或使用明确的事务 ID；确认前后比较状态指纹，过期请求失败关闭。
- JSON 等持久状态使用“同目录临时文件 → flush → 重新读取验证 → 原子替换 → 已验证 `.bak`”流程。
- 失败、取消、停止、等待确认和已完成是不同状态；接受请求不等于任务完成。
- 用户原有文件、暂存区、会话、草稿和设置默认保留；删除优先进入回收站或保留可验证回滚点。

### 凭据和隐私

- API Key 只经 Windows DPAPI 加密存储和内存通道使用，不写入代码、日志、普通诊断、终端环境或安装包。
- 代理 URL 拒绝凭据；回环服务和终端不经过软件外部代理。
- 支持包、备份、截图、测试夹具和错误信息都不得包含完整路径、会话正文、命令正文或令牌。
- Full Access 只由用户明确选择，DSH 不自动提升权限或自动批准 Harness 请求。

## 4. UI 与交互规范

- 保留官方 Harness 主对话和官方控制；DSH 只优化自己拥有的工作台层。
- 状态同时使用文字和图标，不能只依赖颜色；错误必须说明影响、保留的数据和下一步操作。
- 所有操作支持合理的键盘路径、可见焦点、Escape 取消和焦点恢复。
- 新 UI 同时覆盖高对比、系统强制色、减少动画和 1024×720/窄宽度场景。
- 文件拖放必须处理完整 `dragenter`、`dragover`、`dragleave`、`drop` 生命周期；文档、图片和普通文本各自保留正确路由。
- 危险操作使用原生确认且默认取消；取消后界面恢复到真实已保存状态。
- 不显示无法执行的主操作；只读、保护、空状态和加载状态不能伪装成可点击成功路径。

## 5. 测试规范

- 测试名称描述用户可观察行为，不绑定无意义的内部实现细节。
- 每个功能至少有成功、失败/拒绝、边界值和状态变化测试；涉及异步时覆盖切换、重复请求和过期响应。
- 使用临时目录和独立 Git 身份，测试不得依赖执行顺序、个人目录、已有会话或真实凭据。
- 源码字符串断言只用于守护固定边界；关键 IPC、进程、文件、Git、拖放和安装行为需要真实或集成测试。
- UI 测试检查控件存在、状态语义、ARIA/焦点和禁止能力；视觉变化再补真实截图，不以截图替代行为测试。
- 真实模型测试只用于本地可控的关键链路，并使用随机标记验证结果；不得记录或打印 Key。

## 6. 代码审查规范

### 审查顺序

1. 用户问题、版本范围、明确不做什么。
2. Harness 与 DSH 的职责是否放对位置，是否产生重复实现。
3. 数据流和特权边界：Renderer → Preload → Main → Harness/文件/进程。
4. 正确性：空值、边界、竞态、切换、取消、恢复和幂等。
5. 安全与隐私：输入、路径、IPC、凭据、代理、日志、备份。
6. 测试质量与发布影响。

### 严重级别

- **Blocking**：数据丢失、越权、凭据暴露、跨 Workspace 操作、错误成功状态、无法回滚或核心功能回归。
- **Important**：明显维护性风险、未覆盖竞态、无障碍阻断、包/状态不一致，应在当前版本解决或明确接受。
- **Nit**：命名、局部可读性和非阻断一致性。
- **Suggestion**：可选改进，不阻断当前版本。

每条意见写清“位置、触发条件、影响、建议修复和需要的验证”。审查结论只能是通过、带非阻断意见通过或要求修改，不能用模糊评价代替决定。

## 7. Definition of Done

一个 DSH 小版本只有同时满足以下条件才算完成：

- [ ] 用户问题和版本边界明确，上游重复能力已核对。
- [ ] 实现和回归测试完成，完整测试与生产依赖审计通过。
- [ ] 代码审查无未解决 Blocking。
- [ ] 安装包、摘要、解包冒烟和覆盖安装通过。
- [ ] 已安装应用专项验证通过，用户数据与凭据边界验证通过。
- [ ] Release Notes、README、PROGRESS 和 Wiki 已同步。
- [ ] 发布状态准确；未得到确认时不推送 GitHub、不晋升 Stable。

## 8. 提交与 PR

- 分支默认使用 `codex/<版本或主题>`。
- 提交使用 `feat:`、`fix:`、`docs:`、`test:`、`refactor:` 或 `chore:` 前缀，描述一个可审查意图。
- 优先将人工编写变更控制在 200–400 行；更大改动应按接口/实现/集成拆分，或在 PR 中解释不能拆分的原因。
- 不提交安装包、运行时缓存、用户日志、会话、凭据或与当前版本无关的本地文件。
- PR 必须写明问题、方案、边界、测试证据、UI 截图（如适用）、数据迁移/回滚和发布影响。
