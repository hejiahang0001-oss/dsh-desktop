Preparation: `node scripts/prepare-harness021-candidate.cjs --source-root=<absolute-clean-exact-checkout>`. Only use an isolated checkout with no user data. Preparation success proves input application, not security acceptance, runtime compatibility or deployment.

Preparation rejects hard links and directory links, validates patch pre/postimages before changes, and stages/flushed-verifies the lock before atomic replacement. New files must be explicitly declared once in `addedFiles`, match pinned input/postimage bytes, have an absent destination, and belong to the exact allowlist: the HCS patch and the reviewed private PowerShell helpers (`win32-process/extension-points.ts`, `sandbox-windows-acl/private-console.ts`, `sandbox-windows-acl/pty-console.ts`, `sandbox-local/private-powershell.ts`, each under its package `src/`). Allowlisting does not integrate a proposal or relax `promotionAllowed`; the actual profile and patch determine what is prepared. A final replacement failure only reverses the patch while all reviewed bytes and Git state still match; newly created file identity is also checked so same-byte replacement is preserved. Concurrent changes produce an explicit partial-state error and are preserved. This is not a crash-recovery transaction guarantee.

New source removes the old runtime-invariant companion and its validation script. A future candidate builder must retain the relevant current build/packaging checks, not just delete a failing command. Default automation can reactivate persisted active tasks; never test the new kernel with a real user home before validating migration and backup boundaries. Lulu's compiled DOM selectors still require a new-target UI check.
